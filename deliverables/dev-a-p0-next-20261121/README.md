# USER 적용 패킷 — 남은 P0 (46 → 54)

외부 적용·배포 명령은 수행하지 않았다. 기존 패킷/마이그레이션을 수정하지 않은 새 증분 패킷이다. 정확한 대상 소스 SHA와 SQL 해시는 MANIFEST.json을 기준으로 한다. 저장소 push workflow는 검증만 실행하며 호스팅의 별도 자동화 결과를 배포 성공으로 추정하지 않는다. main merge/실제 배포는 USER가 조율한다.

1. USER가 대상 Supabase SQL Editor에서 `00_preflight.sql`을 실행한다. 정확한 기존46 이력과 핵심 함수 정의가 다르면 STOP이다. 이력을 지우거나 강제로 맞추지 말고 개발자가 실제 상태에 맞는 새 패킷을 준비한다. 적용 전 백업/복구 가능 여부는 별도 릴리스 게이트다.
2. 통과한 경우 같은 대상의 `01_apply_current_46.sql` 전체를 한 번 실행한다. 단일 트랜잭션이며 오류 시 전체 롤백한다. 기존 데이터에 민감한 공개 브랜드 소개가 있으면 자동 삭제하지 않고 중단한다. 운영 검토·공개 철회 후 재검증한다.
3. `02_verify.sql`로 이력54, 정책 active=false, source runtime policies=0, consent boundary=false, TEST billing=false, RLS 누락0을 확인한다. 다른 값이면 실제 결과를 개발자가 검토한다. 기존 대상에서 TEST billing이 켜져 있었다면 이 패킷은 이를 임의 변경하지 않는다. 무료 릴리스에 맞는 USER 차단 결정이 필요하다.
4. 개발자가 MANIFEST의 소스를 검증하고 USER가 배포 시점을 조율한다. 새 화면은 실제 승인 정책 없이는 신규 가입을 열지 않는다. 실제 URL·정책 steward 검토 후 USER가 `03_activate_after_source_review.sql`을 실행하면 예전 직접 Auth 가입도 필수 확인 없이 통과하지 못한다. 활성화는 단방향이고 최초 소스/시각을 보존한다. 03은 정책 내용 승인이나 수집 활성화를 수행하지 않는다.

**스테이징은 보안·정책 완료가 아니다.** 01 직후에는 구버전에서 metadata 없이 가입하던 동작을 유지하지만 그 계정에 동의를 소급 생성하지 않는다. 새 metadata를 보내는 가입에는 개별 필수 확인·정책 버전/해시 검증을 적용한다. 이 임시 상태를 공개 릴리스 완료로 보고하지 않는다. 원본054를 별도로 적용하면 기본 strict=true다. 패킷과 원본을 중복 적용하지 않는다.

USER가 제공할 사실은 실제 수집·보존 항목/근거/기한, Supabase/Vercel 및 선택적 처리자 계약·리전·국외이전, 권리 행사/예외/연락 절차다. 현재 정책은 검토본이다. 로컬 `FICTIONAL` 승인이나 테스트 정책을 운영에 복사하지 않는다. 확정된 내용의 새 snapshot/hash 및 추가 SQL은 개발자가 준비한다. USER에게 소스 수정·터미널·패키지 설치를 요구하지 않는다.

수집 정책도 기본 비활성이다. D017/D019의 승인·실제 공급자 확인 전 새 runtime policy를 생성하거나 worker/cron을 켜지 않는다. TTL·tombstone·일일 내부 한도는 승인된 정책 값이며 임의로 법정 기간이라 단정하지 않는다. 일일 작업 가중치175는 보수적인 내부 예산이다. Google 실제 과금/할당량 단위가 아니다. 별도 검색 호출은 rolling24h cap으로 제한하며 실제 프로젝트 한도는 USER가 확인한다. 현재 [공식 YouTube 할당량 표](https://developers.google.com/youtube/data/determine_quota_cost)는 search와 일반 API 버킷을 구분한다.

새 환경변수·API 키·유료 설정은 없다. 계정 전체 삭제 D014는 계약 모듈만 준비됐고 실제 삭제 API/어댑터·보존 예외·기존 signed URL 무효화·백업 재삭제가 남는다. 선택적 공개 철회를 계정/파일 전체 파기로 안내하지 않는다. 외부 SMTP·권리 승인·실제 URL 검증과 DEV-B 리뷰도 별도다.

D073도 부분 진행이다. 가입3목적·설정의 전역 공개 철회는 원장에 연결했지만 기존 profile/brand의 각 공개 저장은 기존 owner_consent/published 경로다. 공개 동의 부여/철회를 원장 버전과 원자적으로 연결하는 후속 개발·직접 REST 검증이 남는다. 이 패킷을 모든 공개 동의 흐름의 완성으로 승인하지 않는다.

검증: `harness/evidence/DEV-A-P0-NEXT-20261121/`와 티켓별 `VERIFY_NEXT_20261121.md`. 실제 생성 SQL의 로컬46→54 적용/데이터 보존/오류 롤백/중복 거부/단방향 활성화를 독립 DB에서 검사했다. 로컬 Auth 역할 검사는 실제 외부 SMTP·공급자 승인 증거가 아니다.
