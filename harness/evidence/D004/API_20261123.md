# D004 — bounded request and response compatibility supplement

Base: main `d79235d`, D003 follow-up `a90c1d1`. The common API layer now reads bounded actual bytes before JSON/schema processing, including absent/false Content-Length and streamed requests. Default 1MiB accommodates the existing 100KB CSV after JSON escaping. Every compatible-handler body is bounded regardless of media type, preventing a forged multipart/text header from bypassing JSON limits. Uploads retain their existing 5MiB file limit plus64KiB multipart envelope; retention restores have an explicit4MiB bound. Authentication, MIME/ownership checks and schema validation remain in their handlers.

Redirect/fetch responses are copied before adding the server-generated request ID, preserving immutable headers, Location, body, status and route context. Malformed JSON remains400, schema rejection422, oversized body413 with `PAYLOAD_TOO_LARGE`; raw body/provider/exception contents are not returned.

Affected verification: `vitest run tests/api-errors.test.ts tests/campaign-api.test.ts tests/admin-api.test.ts tests/intelligence-api.test.ts` — 50 tests/4 files PASS on Node22. Includes exact/over byte boundaries, Korean UTF-8, false lengths, stream cancellation, media spoofing, real FormData forwarding, redirects, dynamic route context, roles and sanitized errors. Role/DB results here use unit stubs, not actual provider/database acceptance. Full shared and desktop/mobile HTTP checks follow in the batch receipt.

SQL and external configuration unchanged. Status remains TESTED; target-environment/full-role regressions and deployment acceptance are not claimed. No security test was skipped and no permission/source gate was removed.
