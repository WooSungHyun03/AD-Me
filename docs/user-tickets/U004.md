# U004 — Supabase 외부 환경·DB 변경 적용

담당: 사용자 · 우선순위: P0 · 현재 상태: USER_ACTION_REQUIRED · 기준일: 2026-11-19

이 문서는 외부 작업의 실행 명세다. 문서 작성만으로 설정/승인/배포가 완료된 것은 아니다. 이전에 설정한 항목은 현재 상태를 확인해 증거를 남기면 재작업하지 않아도 된다.

## 목적·완료 조건

개발자가 제공한 검토된 마이그레이션·RLS·Storage·Edge Function 변경을 외부 서비스에 적용한다. 적용 로그만 공유한다.

## 시작 전에 개발자가 준비할 것

D018/D075/D085가 검토한 release packet: commit·migration 파일·순서·checksum·사전조건·영향·검증 SQL·복구 계획·Edge Function 산출물. 아직 제공 전에는 실행하지 않는다.

## 사용자가 수행할 순서

1. 대상 ref와 환경, 적용할 commit·migration 파일 목록을 릴리스 자료와 대조한다. 기존 001~003 적용 기록을 확인하고 이미 적용된 SQL을 무조건 다시 실행하지 않는다.
2. D087 기준으로 검증 가능한 백업/복구 지점과 영향 범위를 확보한다. 실서비스 데이터의 삭제/재생성이 포함되면 적용을 중단해 재검토한다.
3. Supabase SQL Editor에서 개발자가 제공한 검토된 SQL만 순서대로 적용한다. 파일을 임의 수정하지 않는다. SQL Editor 적용은 CLI migration history와 다를 수 있으므로 파일명/checksum/적용시각/결과를 기록하고 D085가 이력을 조정하도록 인계한다.
4. RLS/GRANT/RPC/Storage는 함께 적용하고 검증 SQL 결과를 확인한다. RLS를 끄거나 service-role을 브라우저에 넣어 오류를 해결하지 않는다.
5. Edge Function 변경이 포함되면 Dashboard에서 현재 지원하는 배포 기능으로 검토된 소스를 적용한다. UI 배포가 지원되지 않으면 미리 구성된 사용자 수동 승인형 워크플로를 개발자에게 요청하고 사용자 본인이 승인한다. 사용자에게 CLI 실행을 요구하지 않는다.
6. 환경값은 U006에서 직접 등록하고 function 인증 설정을 개발자의 JWT 검증 방식과 대조한다. framework 버전과 다른 JWT 설정을 추측으로 바꾸지 않는다.
7. 개발자의 직접 API 권한 검사·마이그레이션 후 검증을 요청한다. 실패한 일부 migration을 전부 성공으로 기록하지 않는다.

## 검증·개발자 인계

ref·commit·파일명/checksum·적용 순서·시각·성공/실패 로그(마스킹)·검증 SQL 요약·function 배포 버전.

위 정보를 해당 개발 티켓 담당에게 전달한다. 성공 여부는 계정 화면의 설정과 실제 기능 검증을 함께 확인한다. 비밀값은 전달하지 않는다.

## 실패·중단·복구

부분 실패는 다음 SQL 적용을 멈추고 로그와 적용 범위를 전달한다. DB는 프런트 롤백으로 돌아가지 않는다. 검토된 forward fix/복구만 실행한다.
